# ADR 0008: Spry on Google Cloud — a GCP service for every piece

- **Status:** accepted (for the core); stretch goals proposed
- **Date:** 2026-11-26
- **Context:** Lab 9. Spry runs on AWS and is described in Terraform (`infra/`, ADR 0007).
  The question: what would it take to run the same system on Google Cloud, and what would it cost?
- **Note:** I did not open a Google Cloud account (it needs a card). The `gcp/` configuration is
  written and passes `terraform validate`; the app is run locally the way Cloud Run would run it
  (`docker-compose.cloudrun.yml`).

## Decision, piece by piece

| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront (Free plan) + WAF, static frontend | Firebase Hosting | **Replace** | CDN and managed HTTPS certificate included, free plan is enough. A Cloud Storage bucket alone has no HTTPS on a custom domain without a load balancer billed by the hour. Firebase also rewrites `/api/**` to Cloud Run, so the browser sees one origin and needs no CORS, as CloudFront did. |
| Lambda + function URL, FastAPI (Lambda Web Adapter) | Cloud Run | **Replace** | The same FastAPI container, scales to zero, HTTPS URL included. The Lambda adapter is removed (`backend/Dockerfile.cloudrun`): Cloud Run sends plain HTTP to `$PORT`. No code change in the app. |
| ECR | Artifact Registry | **Replace** | 0.5 GB free; a cleanup policy keeps the 3 newest images so we stay inside it. |
| Aurora Serverless v2 (0–1 ACU, pauses) | Cloud SQL for PostgreSQL, `db-f1-micro`, 10 GB SSD | **Replace** | Keeps PostgreSQL, so SQLAlchemy models, Alembic migrations and queries move unchanged. Cost: Cloud SQL does not pause. Mitigated by stopping it when nobody uses it (`db_activation_policy = "NEVER"`). See *The database* below. |
| — (we did not move to DynamoDB) | Firestore | **Not chosen** | Would make an idle month free, but means rewriting the data layer (no joins, no foreign keys, no migrations). |
| Cognito user pool + Google | Identity Platform | **Keep on AWS for now** (stretch: replace) | The API already verifies Cognito ID tokens; it keeps doing that from Cloud Run (`COGNITO_*` variables). Identity Platform would give 50,000 free MAU instead of 10,000, but users would have to be migrated or sign up again. |
| EventBridge Scheduler | Cloud Scheduler | **Keep on AWS for now** (stretch: replace) | Weekly report is a stretch goal. On GCP: one job (3 are free) calling a Cloud Run endpoint. |
| SQS | Pub/Sub push to Cloud Run (or Cloud Tasks) | **Keep on AWS for now** | Our queue is a work queue for one consumer, so Cloud Tasks is the closer match; Pub/Sub push is the simpler choice if more consumers appear. |
| S3 event → Lambda | Cloud Storage + Eventarc → Cloud Run | **Keep on AWS for now** | Part of the reports flow. |
| SES | no Google service → SendGrid / Mailgun, or keep SES | **Keep SES** | See *E-mail* below. |
| Bedrock (Claude, Nova) — agenda parser | Vertex AI (Gemini, Claude via Model Garden) | **Keep on AWS for now** (stretch: compare) | Same Claude models exist on Vertex AI, but trial credit does not pay for partner models. |
| SSM Parameter Store / Secrets Manager | Secret Manager | **Replace** | The database URL (with a password generated by Terraform) is a secret; the API's service account can read only that secret. 6 versions free. |
| CloudWatch Logs | Cloud Logging | **Replace** | Automatic for Cloud Run; nothing to configure. |
| IAM roles | Service accounts + IAM roles | **Replace** | One account for Terraform, one (`spry-api`) the API runs as with only `cloudsql.client` and access to its one secret. Not the default compute account (it has Editor). No JSON keys: gcloud application default credentials locally, Workload Identity Federation in CI. |
| Terraform `aws` provider (`infra/`) | Terraform `google` provider (`gcp/`) | **Add, separately** | Own folder and own state (a second HCP Terraform workspace), so one plan cannot break both clouds. APIs are enabled from Terraform, so a fresh project is reproducible. |

## The database

| Option | Latency | Bill (idle month) | Code |
|---|---|---|---|
| Cloud SQL running around the clock | Lowest: unix socket from Cloud Run in the same region | ≈ $9.40 (instance $7.67 + 10 GB SSD $1.70) | No change |
| **Cloud SQL stopped when not in use** (chosen) | Same while running; first request after a start waits for the instance (a minute or more) | ≈ $1.70 (storage is billed while stopped) | No change; starting/stopping is `terraform apply -var db_activation_policy=...` or a Cloud Scheduler job |
| Firestore | Low, but each screen may need several reads | $0 within the daily free quota | Rewrite models, queries and migrations as documents |
| Keep Aurora on AWS, call it across clouds | +20–80 ms per query (us-central1 ↔ us-east-1), several queries per request | Aurora stays ≈ $0 paused, but egress from GCP and AWS is billed, and Aurora must be reachable from the internet or through a VPN | No change, but the security and the latency get worse |

**Decision:** Cloud SQL `db-f1-micro`, stopped outside demos. Spry is relational (meetings, participants,
the many-to-many link, owners), and the point of the exercise is to move without rewriting.
Paying ~$1.70 a month for storage is cheaper than rewriting the data layer for Firestore. Calling
Aurora across clouds is rejected: every API request makes several queries, and each would cross
the continent.

Data: an empty database plus migrations (`alembic upgrade head` runs when the container starts),
then `app.seed` for sample data. For real data the path would be `pg_dump` from Aurora and
`psql`/`gcloud sql import` into Cloud SQL.

## E-mail

Keep **SES** (multicloud is allowed): the weekly-report e-mail is the part that stays on AWS anyway.
If the reports move to GCP, use **SendGrid** (or Mailgun) through its HTTP API. Its API key lives in
**Secret Manager**, readable only by the service account of the service that sends mail, and is
injected as an environment variable like `DATABASE_URL`. Never in the repository or in Terraform variables.

## What we would not move, and why

- **Sign-in (Cognito).** Moving users between identity providers means a password reset or a
  re-sign-up for every user; the API can verify Cognito tokens from any cloud.
- **The weekly report (SQS + S3 + SES).** It is asynchronous, nobody waits for it, and it already
  works. Moving it brings no benefit for users, only work.
- **The agenda parser (Bedrock).** The same Claude models are on Vertex AI, but the trial credit
  does not cover them; we would move it only if Gemini gave the same quality cheaper.

## Consequences

- The core (frontend, API, database) runs on GCP with **no change to application code**: only a
  Dockerfile without the Lambda adapter and new environment variables. The lock-in was in the
  infrastructure around the code (Lambda adapter, CloudFormation/Terraform resources), not in the app.
- Until the stretch goals are done the system is **multicloud**: Cloud Run calls Cognito (JWKS) and
  the report flow stays on AWS. This is a migration state, not a target: two bills, two consoles,
  two sets of credentials.
- The database no longer pauses by itself: someone (or a scheduler) must stop it. A forgotten
  running instance is ≈ $9.40 a month.
